The actual API.

Everything from the previous page, minus the doors and the dramatic lighting. Resource groups, a handful of endpoints, and none of them require you to believe in metaphors.

Base URL https://us.unmanned.team

Authentication

Two steps: trade a client ID and secret for a token, then send that token on everything else. Nothing exotic — a standard client-credentials exchange.

POST /auth/token 200 OK

Exchanges a client ID and secret for a bearer token. Email go@unmanned.team to get credentials if you don't have them yet — this is the first call you'll ever make.

ParameterInTypeDescription
client_idbodystringRequiredIdentifies your workspace.
client_secretbodystringRequiredKeep this out of client-side code. Same rules as any other secret.
requestShell
curl -X POST https://us.unmanned.team/auth/token \
  -H "Content-Type: application/json" \
  -d '{"client_id":"$CLIENT_ID","client_secret":"$CLIENT_SECRET"}'
responseJSON
{
  "access_token": "eyJhbGciOi...",
  "token_type": "bearer",
  "expires_in": 3600
}

Tokens are short-lived on purpose. Cache one until it's within a few minutes of expiring, then call this again — don't request a fresh token on every API call.

Using the token

Every other request in this reference carries that token as a bearer header. Scoped to one workspace — no per-request signing, no separate keys per endpoint.

auth-header.sh Shell 
curl https://us.unmanned.team/monitor \
  -H "Authorization: Bearer $VEX_TOKEN"

Tokens expire on their own; there's no need to rotate them by hand. Rotate the underlying client secret if it ever leaks.

Delegating into an account

By default every call in this reference runs against your root tenant account — the one tied to your own account domain. If you manage other accounts, you can redirect any call to one of them.

Account header

Pass an account header on any request in this doc and Vex delegates that call into the named account instead of your root tenant. Accounts are named after domains — example.com, not an internal ID.

You need permission to manage the account you're delegating into. Omit the header and everything runs against your own account domain, same as always.

HeaderInTypeDescription
accountheaderstring, domainOptionalThe customer account to delegate into, e.g. example.com. Requires permission on that account. Omit to run against your root tenant.
delegate.shShell
# Runs against example.com instead of your own account
curl https://us.unmanned.team/monitor \
  -H "Authorization: Bearer $VEX_TOKEN" \
  -H "account: example.com"

This applies to every endpoint in this reference the same way — monitors, signals, assets, files, all of it. One header, no separate delegated tokens to manage.

Signals

Everything a monitor noticed, and whether Vex thinks it's part of something bigger. This is the part that actually finds the way in.

GET /signal 200 OK

Every signal Vex has collected, newest first. Query params exist so you don't have to scroll forever.

ParameterInTypeDescription
sincequerystring, ISO 8601OptionalOnly return signals detected after this timestamp.
monitorquerystringOptionalFilter to one monitor's signals.
severityqueryinfo, warn, criticalOptionalFilter by how worried you should be.

Threat

The "nothing personal" part, quantified. A running count of the automated noise currently aimed at your business, whether or not any of it went anywhere.

GET /threat 200 OK

A live summary of attempts against your business over a given window: how many, what kind, and where they were aimed. Nobody researched you specifically; this is the receipts.

ParameterInTypeDescription
windowquery1h, 24h, 7dOptionalHow far back to look. Defaults to 24h.
responseJSON
{
  "window": "24h",
  "attempts": 1842,
  "blocked": 1842,
  "top_vector": "credential_stuffing",
  "top_target": "email",
  "last_attempt_at": "2026-08-31T03:14:00Z"
}

"Blocked" means it never got past the front door. It does not mean nobody tried the handle.

Monitors

Connect, check, and disconnect the things watching your business. Slugs match the site: google, microsoft, aws, cloudflare, level, shopify, quickbooks, hubspot, constant-contact, slack, squarespace, and the many more we didn't have room to list here either.

GET /monitor 200 OK

Lists every monitor currently connected to your account. This is the "yes, it's still working" button.

responseJSON
[
  {
    "name": "google",
    "status": "active",
    "connected_at": "2026-06-02T14:11:00Z",
    "last_signal_at": "2026-08-27T22:04:12Z"
  },
  {
    "name": "slack",
    "status": "active",
    "connected_at": "2026-06-02T14:12:40Z",
    "last_signal_at": null
  }
]
POST /monitor/{name} 201 Created

Connects a new monitor. It wants credentials, not your firstborn.

ParameterInTypeDescription
namepathstringRequiredMonitor slug, e.g. google or microsoft.

Body shape depends on the provider. The two most common patterns:

connect-monitor.js JavaScript 
// Google Workspace: service account JSON key
await fetch(`${BASE}/monitor/google`, {
  method: 'POST',
  headers, // Authorization: Bearer <token>
  body: JSON.stringify({
    type: 'service_account',
    project_id: 'your-project-id',
    private_key_id: '...',
    private_key: '-----BEGIN RSA PRIVATE KEY-----\n...',
    client_email: 'vex@your-project.iam.gserviceaccount.com',
  }),
}).then(r => r.json());

// Microsoft 365: app registration credentials
await fetch(`${BASE}/monitor/microsoft`, {
  method: 'POST',
  headers,
  body: JSON.stringify({
    tenant_id:     'your-tenant-id',
    client_id:     'your-app-client-id',
    client_secret: 'your-app-secret',
  }),
}).then(r => r.json());
responseJSON
{
  "name": "google",
  "status": "active",
  "connected_at": "2026-08-28T09:00:00Z"
}
GET /monitor/{name} 200 OK

Status of a single monitor: when it connected, when it last checked in, and whether it's actively watching or having a moment.

responseJSON
{
  "name": "google",
  "status": "active",
  "connected_at": "2026-06-02T14:11:00Z",
  "last_signal_at": "2026-08-27T22:04:12Z",
  "last_checked_at": "2026-08-28T08:59:47Z"
}
DELETE /monitor/{name} 204 No Content

Disconnects a monitor. Vex stops watching that surface immediately. We'll miss it more than you will.

Assets

The inventory Vex has built of your business from the monitors you've connected: domains, identities, endpoints, whatever else showed up. This is what "surface" actually refers to everywhere else in this reference.

GET /asset 200 OK

Every asset Vex currently knows about, across every connected monitor. No filtering needed to get the full picture — this is the full picture.

    "id": "ast_2c91af",
    "type": "identity",
    "value": "jsmith@acmecorp.com",
    "source": "google",
    "first_seen_at": "2026-06-02T14:11:00Z"
  },
  {
    "id": "ast_77d0e1",
    "type": "domain",
    "value": "acmecorp.com",
    "source": "cloudflare",

Assets accumulate as monitors connect and never get removed automatically — disconnect the monitor if one stops being relevant.

Breach

Scenarios built from your assets showing up in breach data — where the exposure came from, and what it actually touches on your side.

GET /breach 200 OK

Every breach scenario Vex has assembled for your assets, newest first.

responseJSON
[
  {
    "id": "brc_44a9f0",
    "source": "third_party_breach",
    "breach_name": "vendorx-2024",
    "breach_date": "2024-03-11",
    "exposed_assets": ["ast_2c91af"],
    "exposed_fields": ["email", "password_hash"]

]

A breach scenario doesn't mean the credential still works — just that it exists somewhere it shouldn't. Cross-reference against signals to see if anyone's tried it.

Notifications

Not signals about your business — signals about Vex itself. Expired credentials, a monitor that stopped checking in, anything that means the watching has a gap in it.

GET /notification 200 OK

Every open notification about your Vex setup: broken auth, a stalled monitor, anything worth fixing before it becomes a blind spot.

responseJSON
[
  {
    "id": "ntf_5e18c2",
    "type": "monitor.auth_expired",
    "severity": "warn",
    "monitor": "microsoft",
    "message": "App registration secret expired, reconnect to resume monitoring",
    "created_at": "2026-08-30T11:02:00Z"
  }
]

These are about the plumbing, not the threat landscape — see Threat and Signals for that.

Files

Reports, exports, and anything else Vex generates and hands back to you, organized into namespaces the same way you'd organize a directory tree.

GET /file/{namespace} 200 OK

Lists the files inside a namespace. namespace is optional — omit it to list from the root.

ParameterInTypeDescription
namespacepathstringOptionalDirectory-style path, e.g. reports/2026-08. Omit for the root namespace.
responseJSON
[
  {
    "name": "monthly-summary.pdf",
    "namespace": "reports/2026-08",
    "size_bytes": 184320,
    "created_at": "2026-09-01T04:00:00Z"
  }
]
GET /file/{namespace}?name={file} 301 Moved Permanently

Downloads a specific file. Add the name query param and the response becomes a redirect instead of a listing.

ParameterInTypeDescription
namespacepathstringOptionalDirectory-style path the file lives in.
namequerystringRequiredThe file name inside that namespace.
requestShell
curl -L https://us.unmanned.team/file/reports/2026-08?name=monthly-summary.pdf \
  -H "Authorization: Bearer $VEX_TOKEN" \
  -o monthly-summary.pdf

The 301 points to a pre-signed, time-limited S3 URL that starts the download on its own — follow the redirect (-L in curl) rather than treating the 301 itself as an error.

Audit

Raw SIEM log lines, for whoever needs to look at the actual record instead of Vex's take on it.

GET /audit 200 OK

SIEM log entries collected across your connected monitors over the requested window.

ParameterInTypeDescription
hoursqueryintegerOptionalHow many hours back to pull logs for. Defaults to 24.
responseJSON
[
  {
    "id": "aud_0f3b21",
