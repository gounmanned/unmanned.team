Authentication

Two steps: trade your username and password for a token, then send that token on everything else. Nothing exotic: a standard AWS Cognito exchange.

POST

cognito-idp.us-east-2.amazonaws.com

200 OK

Exchanges your username and password for a bearer token via AWS Cognito. This call goes straight to Cognito, not the VEX base URL. Email go@unmanned.team to get credentials if you don’t have them yet. This is the first call you’ll ever make.

ParameterInTypeDescription
ClientIdbodystringRequiredIdentifies your workspace.
USERNAMEbody, AuthParametersstringRequiredYour VEX account email.
PASSWORDbody, AuthParametersstringRequiredKeep this out of client-side code. Same rules as any other secret.
requestShell
curl https://cognito-idp.us-east-2.amazonaws.com/ \
  -H "Content-Type: application/x-amz-json-1.1" \
  -H "X-Amz-Target: AWSCognitoIdentityProviderService.InitiateAuth" \
  -d '{"AuthFlow": "USER_PASSWORD_AUTH", "ClientId": "2314edi18c3o3t8sroh2u2hucf", "AuthParameters": {"USERNAME": "you@yourcompany.com", "PASSWORD": "your-password"}}'
responseJSON
{
   "AuthenticationResult" : {
      "IdToken" : "eyJraWQiOi...",
      "AccessToken" : "eyJraWQiOi...",
      "RefreshToken" : "eyJjdHkiOi...",
      "TokenType" : "Bearer",
      "ExpiresIn" : 28800
   },
   "ChallengeParameters" : {}
}

Cognito also returns AccessToken and RefreshToken alongside IdToken. VEX only checks IdToken, so the other two can be ignored for these examples. Tokens are short-lived on purpose. Cache the IdToken until it expires, then call this again. Don’t request a fresh token on every API call.

Using the token

Every other request in this reference carries that token as a bearer header. Scoped to one workspace: no per-request signing, no separate keys per endpoint.

save-token.shShell
export VEX_TOKEN=$(curl https://cognito-idp.us-east-2.amazonaws.com/ \
  -H "Content-Type: application/x-amz-json-1.1" \
  -H "X-Amz-Target: AWSCognitoIdentityProviderService.InitiateAuth" \
  -d '{"AuthFlow": "USER_PASSWORD_AUTH", "ClientId": "2314edi18c3o3t8sroh2u2hucf", "AuthParameters": {"USERNAME": "you@yourcompany.com", "PASSWORD": "your-password"}}' \
  | jq -r '.AuthenticationResult.IdToken')

Every curl example in this reference assumes $VEX_TOKEN is already set this way. Run it once per session and the rest just work.

auth-header.shShell
curl https://4ycv63am8b.execute-api.us-east-2.amazonaws.com/source \
  -H "Authorization: Bearer $VEX_TOKEN"

Tokens expire on their own; there’s no need to rotate them by hand. Rotate your password if it ever leaks.

One login, many accounts: the account header

If you manage other accounts, you don’t need a login for each one. Use the same token, and add an account header to say which account a call is for.

Account header

Pass the account header on any request and the call runs inside that account instead of your own. Accounts are named by their domain, like example.com, not an internal ID.

It works the same on every endpoint in this reference: signals, sources, identities, notifications, files and audit. Leave it out and the call runs against your own account.

You need permission to manage the account you name. To see every managed account at once instead of one at a time, use the managed routes.

HeaderInTypeDescription
accountheaderstring, domainOptionalThe account to run the call in, e.g. example.com. Requires permission on that account. Leave it out to use your own account.
delegate.shShell
# Lists the sources in example.com instead of your own account
curl https://4ycv63am8b.execute-api.us-east-2.amazonaws.com/source \
  -H "Authorization: Bearer $VEX_TOKEN" \
  -H "account: example.com"

Signals

Everything a source noticed, and whether VEX thinks it’s part of something bigger. Signals represent actionable security weaknesses.

Signal status values

The status field tracks where a signal sits in the help desk workflow, from first appearing to however it eventually gets closed out.

CHResolvedConfirmed resolved and archived.

POST

/signal

Creates a new signal. Send all four fields in the body; leaving one out may create an incomplete signal.

ParameterInTypeDescription
statusbodystringRequiredWhere the signal starts, as a status code, e.g. OB for Open.
assetbodystringRequiredWho the signal is about, e.g. priya.shah@acmecorp.com.
sourcebodystringRequiredWhere it came from, as a source slug, e.g. google.
valuebodystringRequiredWhat happened, in plain words.
requestShell
curl -X POST https://4ycv63am8b.execute-api.us-east-2.amazonaws.com/signal \
  -H "Authorization: Bearer $VEX_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "status": "OB",
    "asset": "priya.shah@acmecorp.com",
    "source": "google",
    "value": "Mail forwarding rule sends priya.shah@acmecorp.com inbox to an outside address"
  }'

To add to an existing signal, POST /signal/{id} instead. Only value is read; the other fields are ignored.

Sources

Connect, check and disconnect the things watching your business. Slugs match the site: google, microsoft, aws, cloudflare, level, shopify, quickbooks, hubspot, constant-contact, slack, squarespace, and the many more we didn’t have room to list here either.

Source keys

Every source is identified by a three-part key: account/vendor/index, e.g. acmecorp.com/google/0.

The account is the domain the source belongs to, and vendor is the slug for what it’s watching (google, microsoft and so on). The index tells apart two sources for the same vendor, say two separate Microsoft 365 tenants.

You don’t choose the index: VEX assigns it when you connect a source, and GET /source lists it. You only need it to disconnect a source.

GET

/source

200 OK

Lists every source currently connected to your account. This is the “yes, it’s still working” button.

requestShell
curl https://4ycv63am8b.execute-api.us-east-2.amazonaws.com/source \
  -H "Authorization: Bearer $VEX_TOKEN"
responseJSON
[
  "/acmecorp.com/google/0",
  "/acmecorp.com/slack/0"
]
POST

/source/{name}

201 Created

Connects a new source. It wants credentials, not your firstborn.

ParameterInTypeDescription
namepathstringRequiredSource slug, e.g. google or microsoft. No index: VEX assigns one.

Body shape depends on the provider. The two most common patterns:

connect-source.shShell
# Google Workspace: service account JSON key
curl -X POST https://4ycv63am8b.execute-api.us-east-2.amazonaws.com/source/google \
  -H "Authorization: Bearer $VEX_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "service_account",
    "project_id": "your-project-id",
    "private_key_id": "...",
    "private_key": "-----BEGIN RSA PRIVATE KEY-----\n...",
    "client_email": "vex@your-project.iam.gserviceaccount.com"
  }'

# Microsoft 365: app registration credentials
curl -X POST https://4ycv63am8b.execute-api.us-east-2.amazonaws.com/source/microsoft \
  -H "Authorization: Bearer $VEX_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "tenant_id": "your-tenant-id",
    "client_id": "your-app-client-id",
    "client_secret": "your-app-secret"
  }'
DELETE

/source/{name}/{index}

204 No Content

Disconnects a source. VEX stops watching that surface immediately. We’ll miss it more than you will.

ParameterInTypeDescription
namepathstringRequiredSource slug, e.g. google.
indexpathintegerRequiredWhich source to disconnect, e.g. 0. GET /source lists each source with its index.
requestShell
curl -X DELETE https://4ycv63am8b.execute-api.us-east-2.amazonaws.com/source/google/0 \
  -H "Authorization: Bearer $VEX_TOKEN"

Notifications

Not signals about your business: signals about VEX itself. Expired credentials, a source that stopped checking in, anything that means the watching has a gap in it.

Files

Reports, exports and anything else VEX generates and hands back to you, organized into namespaces the same way you’d organize a directory tree.

GET

/file/{namespace}

200 OK

Lists the files inside a namespace. namespace is optional: omit it to list from the root.

ParameterInTypeDescription
namespacepathstringOptionalDirectory-style path, e.g. signal/. Omit for the root namespace.
requestShell
curl https://4ycv63am8b.execute-api.us-east-2.amazonaws.com/file/signal/ \
  -H "Authorization: Bearer $VEX_TOKEN"
responseJSON
[
  "signal/4827193650228",
  "signal/9013758204461",
  "signal/6650283917405"
]
GET

/file/{namespace}?name={file}

200 OK

Returns a pre-signed, time-limited download URL for a specific file. Add the name query param and the response becomes this URL instead of a listing.

ParameterInTypeDescription
namespacepathstringOptionalDirectory-style path the file lives in.
namequerystringRequiredThe file name inside that namespace.
requestShell
curl "https://4ycv63am8b.execute-api.us-east-2.amazonaws.com/file/signal?name=4827193650228" \
  -H "Authorization: Bearer $VEX_TOKEN"
responseJSON
{
  "url": "https://vex-file-system.s3.us-east-2.amazonaws.com/acmecorp.com/signal/4827193650228?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Checksum-Mode=ENABLED&X-Amz-Credential=..."
}

The actual file lives at the returned url. It’s a pre-signed, time-limited S3 URL, so fetch it directly (no auth header needed) to download the file itself.

Audit

Raw SIEM log lines, for whoever needs to look at the actual record instead of VEX’s take on it.

GET

/audit

200 OK

SIEM log entries from your connected sources that match your search, or that fall between two times.

ParameterInTypeDescription
qquerystringOptionalWhat to search for, the way you’d search the web, e.g. dmarc. Returns the log lines that match.
startquerystring, ISO 8601OptionalOnly return log lines from this time on, e.g. 2026-10-12T00:00:00Z. Use with end. Ignored when q is set.
endquerystring, ISO 8601OptionalOnly return log lines before this time, e.g. 2026-10-13T00:00:00Z. Use with start. Ignored when q is set.
requestShell
curl "https://4ycv63am8b.execute-api.us-east-2.amazonaws.com/audit?q=dmarc" \
  -H "Authorization: Bearer $VEX_TOKEN"

# or everything between two times
curl "https://4ycv63am8b.execute-api.us-east-2.amazonaws.com/audit?start=2026-10-12T00:00:00Z&end=2026-10-13T00:00:00Z" \
